4. CONFIRMED FORMULA: bond_length simultaneously controls ribose ring
   size, base ring size, AND ribose-to-base attachment reach (Goal 1)
================================================================
Ribose ring's own centroid sits exactly 0.8507 * bond_length from C1'
(regular-pentagon geometry, exact). The base's attachment atom (N9/N1)
sits exactly 1.0 * bond_length from C1' (by construction, unconditional).
For the STRAIGHT/purely-vertical pairing case (no wobble), the distance
between the ribose ring's centroid and the base's attachment point is
therefore exactly:
    bond_length * |1 - 0.8507| = bond_length * 0.1493
At bond_length=10.8: 10.8 * 0.1493 = 1.613 — matches every template-top/
template-bottom row in the pre-play dump exactly.

NOTE (see section 6): this 0.1493 relationship is NOT universal — it only
holds for the specific sign/pairing-direction combination present in
template-template pairing. Leading/lagging show a different, also-
constant value (19.987) for the same underlying quantity. The bond_length
coupling itself (one knob driving all three quantities) IS universal;
which constant it lands on is not.

6. WHY TEMPLATE LOOKS STRUCTURALLY WORSE THAN LEADING/LAGGING (Goal 3) —
   RESOLVED, sign-interaction, not staleness or different code
================================================================
Confirmed NOT a caching/staleness issue (both re-read from live code:
topology fold is cached per "strand:slot" key forever, but ring/base
LOCAL GEOMETRY is recomputed fresh every frame for every strand including
template — verified from molecule_structure_renderer.gd directly).

Confirmed NOT a different code path (same _rebuild_layout() ->
RiboseDeriver / NitrogenBaseDeriver calls for all three).

Root cause: two INDEPENDENT rotations interact.
  - RiboseDeriver.apply_strand_direction()'s 180-degree ribose rotation is
    tied to fixed STRAND IDENTITY (leading is always sign -1, regardless
    of who it's paired with this frame).
  - NitrogenBaseDeriver.derive_base_layout()'s retargeted rotation (fix
    2a above) is tied to the ACTUAL pairing_direction for that residue
    this frame — situational, not fixed per strand.
  For template-top/template-bottom pairing, these two signs combine
  CONSTRUCTIVELY, producing the small 1.613 ribose-to-base offset (heavy
  overlap). For leading-paired-against-template_top and lagging-paired-
  against-template_bottom, the same two rotations combine
  DESTRUCTIVELY instead, producing 19.987 (no overlap). This was
  confirmed identical (19.987) across every leading pair and every
  lagging pair tested, regardless of which specific bases were involved
  — a real, reproducible geometric consequence of the sign relationship,
  not noise.

Earlier in this same investigation I called 1.613 a "universal constant"
before pass 2/3 data existed — that was premature/wrong. It's constant
WITHIN a given pairing relationship (template-template, or leading-
template, or lagging-template), but different ACROSS relationships,
because each relationship has its own fixed sign combination.

7. RESOLVED: leading/lagging showed SAME-LETTER pairs against their
   template partner — confirmed real bug, fixed
================================================================
Every one of the first 10 slots in BOTH the leading/template_top section
and the lagging/template_bottom section showed IDENTICAL letters (AA, TT,
GG — never AT, TA, GC, CG). Investigated and fixed (see
docs/MolecularStructure_BasePairExpansion.md's Bug E entry for the full
account). Root cause confirmed against docs/SKILL.md's own polarity
table: leading's real template is template_top (get_complement(i)), so
leading's own letter must be get_base(i), not get_complement(i) as every
call site had it (and symmetrically for lagging vs. template_bottom).
PARTNER_STRAND and the spatial layout formulas were already correct —
only the base-identity formula was backwards, at 12 call sites in
replication_manager.gd, all now fixed and swapped consistently.

This means every leading/lagging H-bond-span number gathered earlier in
this dump (26.08 for AA/GG pairs, 0.99 for TT pairs) was measuring a
nonsensical purine-purine/pyrimidine-pyrimidine combination the
rotation-retarget fix was never designed for — those numbers should be
discarded, not reused. Re-run the F9 diagnostic dump after this fix to get
real leading/lagging span numbers for genuinely complementary pairs before
making any further bond_length decision.
